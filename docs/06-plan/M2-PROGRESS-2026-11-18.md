## 1. TCP 打洞的 Unix 分支（补 ADR-018 的缺口）

第一轮的遗留项是「Unix 分支（`poll` + `__errno_location`）本机无法编译验证」。
本轮在 `192.168.1.221`（Ubuntu，rustc 1.100.0）上真实编译并运行：

```
running 4 tests
test tcp_punch::tests::empty_peer_list_is_reported_not_guessed ... ok
test tcp_punch::tests::simultaneous_open_on_loopback_establishes_and_carries_bytes ... ok
test tcp_punch::tests::sockaddr_layout_is_network_order ... ok
test tcp_punch::tests::punching_a_closed_port_times_out_without_inventing_success ... ok

test result: ok. 4 passed; 0 failed
```

Linux 上的观测（`--nocapture`）：

```
[tcp-punch] A established=true attempts=7 errors=["向 127.0.0.1:33077 的连接被拒: Connection refused (os error 111)"]
[tcp-punch] B established=true attempts=7 errors=["向 127.0.0.1:45829 的连接被拒: Connection refused (os error 111)"]
```

两点必须记下来，否则会被误读：

1. **`attempts=7` 是正常现象**，不是退化。同时打开要求双方 SYN 在时间窗内交叉；
   先到的一方会收到 RST（`Connection refused`），重试到对端的 SYN 到达才建立。
   Windows 回环上是 `attempts=1`，因为两侧线程调度更快对齐。**跨平台差异体现在重试次数，
   不体现在能否建立。**
2. 这也顺带证明「假阳性判据」在 Linux 上同样必要：早期用 `peer_addr()` 判定时，
   `SYN_SENT` 阶段就会返回目标地址，对空端口也报成功。现在两侧都要求
   `poll(POLLOUT)` + `SO_ERROR=0`，空端口用例（`punching_a_closed_port_times_out...`）明确失败。

**边界**：Linux 证据依旧在**回环**上；公网双侧仍然 `BLOCKED`（A 侧 CPE 未为固定本地端口
建 TCP 映射，UDP 学到的映射端口不能用于 TCP）。BT-over-punched-TCP 在本轮仍未接线
（librqbit 9.1.0 不接受外部 socket）——**状态更新见 §8**：v2.4.87 已用 ADR-021 的
SOCKS5 钩子 + 回环 splice 落地桥接层，但端到端真实样本仍未跑。

## 2. 多任务做种下的逐出路径（真引擎）

第一轮只有 `FakeOps` 单测，属于「我们按约定调了 pause」，不能证明引擎真的停了任务。
本轮新增 `coldrevived::sched::tests::real_engine_eviction_pauses_the_previous_seed`：

- 真实 `RqbitEngine`，两个真实 `.torrent`（`cr_torrent::generate` 生成，96 KiB 各两片）；
- 两个任务都以 `paused=true` 加入（与守护进程的 COLD 语义一致）；
- `LruScheduler::new(1)`，`wake_seed` A → B → A，共三次；
- 断言的是 `Engine::state` 的观测值：`Cold → Hot → Cold → Hot`，以及 `evicted` 字段
  在两次满载时分别指向 A、B。

结果：`test result: ok. 7 passed`（sched 模块全部）。

**它证明了什么**：`wake_seed` 在真实引擎上确实执行「暂停被逐出者 → 激活请求者」，
且暂停在引擎状态中可见，不是只改调度器记账。
**它没证明什么**：守护进程当时仍然只持有一个做种任务（`st.seed_task: Option<TaskId>`），
「多个样本同时存在」在产物里还不成立。因此这仍是**组件级**证据；
「多任务守护进程实测」需要先改产品形态（多 `sample` 入库 + 每任务映射），不在本轮范围。
**状态更新见 §8**：v2.4.87 已完成形态改造（2 个样本真实进程 `/health.seed_tasks=2`）；
但守护进程级逐出仍待签名唤醒复跑。

## 3. 中继真实网络：时延 / 丢包 / 单 IP 限额

### 3.1 测量工具

新增 `coldrevive-relaybench`（`src/bins/coldrevive-relaybench`）：

- **往返阶段**：同进程起 A（发）与 B（回声）两个真实 `RelayClient`，都注册到同一中继；
  A 逐条发帧、等回声，RTT 覆盖「A→中继→B→中继→A」完整一圈；
- **并发阶段**：并发开 N 条 TCP，统计「连上即被对端关闭」的条数——
  这是对服务端 `max_conns_per_ip` 的**外部**观测，不读服务端内部计数；
- 只报测到的数：超时计入 `lost`，不改写成 0 ms；丢包过半则以非零退出码结束。

### 3.2 环境与结果

中继：`192.168.1.221:7100`（Linux，`--allow-insecure`，`max_conns_per_ip=64`，
`register_per_ip_per_min=240`）。客户端：A = `192.168.1.210`（Windows 本机），
C = `192.168.1.222`（Ubuntu，另一台真机）。

| 客户端 | 轮数 / 负载 | 收到 | 丢包 | p50 | p90 | p99 | max |
|--------|-------------|------|------|-----|-----|-----|-----|
| A | 200 / 256 B | 200 | 0 | 0.821 ms | 0.916 ms | 1.117 ms | 1.492 ms |
| C | 200 / 256 B | 200 | 0 | 0.588 ms | 0.810 ms | 5.661 ms | 8.008 ms |

单 IP 上限（并发连接阶段，服务端同一实例、同一时刻配置）：

| 客户端 | 尝试 | 建立 | 被对端关闭 | 服务端 `ip_cap_rejected` 增量 |
|--------|------|------|------------|------------------------------|
| A | 96 | 96 | 32 | +32 |
| C | 80 | 80 | 16 | +16 |

两侧数字**逐条对得上**：96−64=32、80−64=16，说明限额确实是**按来源 IP**计的
（A 与 C 各自有独立配额，不是全局限 64）。

注册频率配额（`--register-per-ip-per-min 6`，同机连续起客户端）：

```
run1: ok
run2: ok
run3: ok
run4: {"ok":false,"error":"A 注册失败: 中继拒绝请求: 注册频率超过单 IP 配额，请退避后重试"}
run5: 同上
```

**范围声明**：这是**局域网真机 + 真中继进程**的测量，不是公网 VPS。
本环境没有可用的公网主机（222 出口为真实 NAT `112.5.32.34`，但 7100 无入向映射），
所以本轮「公网中继时延/丢包」仍未测；把 LAN 数字写成公网结论会直接误导部署容量规划。
**状态更新见 §8**：后续已在公网原生 `7101/UDP` 上量到 840/840、0 丢包，p50 区间 34–52 ms
（见 [M2-VANTAGE](M2-VANTAGE-2026-11-18.md) §3.4）；222 的 `7100/TCP` 也 30/30 全通。

### 3.3 本轮顺带修掉的一个真实缺陷：拒绝时不说明原因

配额触顶时服务端原来**直接关连接**，客户端看到的是：

```
链路错误: 读帧头失败: failed to fill whole buffer
```

这句话会把人引向「网络不稳」，而真实原因是配额。本轮新增 `FrameKind::Reject = 0x0c`：

- 服务端在断开前发一帧 UTF-8 原因（单 IP 注册频率 / 注册表已满 / 同连接改 ID）；
- 客户端 `register` 与 `register_declared` 识别该帧，翻成
  `中继拒绝请求: <原因>`；
- 旧客户端收到 `0x0c` 会当作 `Unknown` 并仍按拒绝处理——**行为与以前一致**，
  不会把拒绝误判成成功；
- 服务端收到客户端回送的 `Reject` 帧时忽略（不断开），避免一条坏帧引发重连风暴。

回归：`registration_rate_limit_per_ip_closes_late_registrations` 现在断言
错误里必须出现「拒绝」和「频率」，把「能区分原因」变成可回归的约束。

## 4. `cr-dht` 连公网引导节点

### 4.1 先修掉的可用性缺陷：只收字面 IP

BEP 5 的引导节点**全部是域名**（`router.bittorrent.com:6881` 等），而工具原来
只接受 `ip:port`，对域名报 `invalid socket address syntax`——看起来像用户写错地址，
实际是工具不支持最常用的一条路径。已加 `parse_target`：先按字面解析，失败再当域名解析，
**只取 IPv4**（DHT socket 是 v4），解析结果在输出里回显（`resolved` 字段），
便于核对「到底打了谁」。3 条单测覆盖字面 / 域名 / 垃圾输入。

### 4.2 只读探测结果

| 目标 | 结果 |
|------|------|
| `dht.transmissionbt.com:6881`（87.98.162.88） | ✅ ping 连续 4/4 成功，`remote_id` 恒定 `3503427510bc…` |
| `get_peers`（随机 infohash） | ✅ 应答含 8 条 compact 节点 |
| `router.bittorrent.com` / `router.utorrent.com` / `dht.aelitis.com` / `dht.libtorrent.org:25401` / `dht.bt.am:2710` | ❌ 全部 2000 ms 超时 |

**结论**：公网 UDP 双向可达（真实请求得到真实应答，`remote_id` 稳定），
KRPC 编解码与 compact 解析在真实网络上成立。这是本项目第一次拿到公网 DHT 应答。

### 4.3 拓扑发现受阻：引导节点返回的节点列表不可用

新增 `--walk <seed[,seed...]>`（只读，不发 `announce_peer`，查询数硬上限）后观测到：

```
{"mode":"walk","seeds":"dht.transmissionbt.com:6881","queried":2,"ping_alive":2,
 "find_node_answered":1,"unique_contacts":1,"frontier_left":0}
```

逐条核查（用**独立 Python 实现**交叉验证，避免把「我方解码 bug」当成服务器行为）：

```
count 8
0 id=54f74e063ded ip=98.28.70.71 port=50980
1 id=54f74e063ded ip=98.28.70.71 port=50980
...（8 条完全相同）
```

连续三轮：应答 `id` 恒定（确为该节点），但 8 条记录**全部指向同一地址**，
且该地址在下一轮就变（`115.138.67.156` / `59.10.24.139` / `23.244.117.210`），
对这些地址 `ping` 与 `find_node` 全部超时。

判定：**不是解码缺陷**（两种独立实现得到同一结果），而是该引导节点的应答本身
不可用于拓扑发现。因此：

- `--walk` 学到的 `unique_contacts` 只有 1，属于**如实反映**，不是「DHT 只能学到 1 个节点」；
- **`announce_peer` 未执行**：① 需所有者明确授权（写入公网 DHT 是外部可见行为）；
  ② 即使授权，当前也拿不到可用邻居，宣告出去无人转发，只会留下一条无效记录。
  记为 **BLOCKED**，理由写明，不用「已尝试」糊过去。

## 5. 环境侧的两个坑（会重复踩，写下来）

1. **221 上 `cargo test` 需要 `libssl-dev`**：`crypto-hash`（librqbit 依赖链）在 Linux 上
   要 openssl 头文件，缺了会在 `openssl-sys` 的 build script 阶段失败，看上去像代码问题。
   已 `apt-get install -y libssl-dev pkg-config`（现装 3.0.8）。
2. **`tar` 同步会保留旧 mtime，cargo 据此复用陈旧 rlib**：
   第一次同步后 221 报 `cannot find function generate_with_announce_list in crate cr_torrent`，
   而两端文件 `md5` 完全一致。原因是 tar 把 mtime 恢复成旧时间，指纹判定「没变」。
   **同步后必须 `touch` 所有 `.rs` 与 `Cargo.toml`**，否则会得到假的编译结论。

## 8. 第三轮补记（v2.4.87 / v2.4.88 / v2.4.89，2026-11-18 晚）

### 8.1 P3：桥接层落地，不换引擎（`cr-bridge`，ADR-021）

- 决策见 [ADR-021](../02-architecture/adr/ADR-021-punched-tcp-bridge.md)：**不 fork、不换引擎**。
  `cr-bridge` 用 librqbit 的 `ConnectionOptions.proxy_url` 作为**出向**钩子——本地 SOCKS5
  命中「已打通注册表」就交出那条 socket，未命中回落**真实直连**；**入向**用
  `splice_to_listener` 把打通的连接接到引擎自己的监听口。
- 6 条真实 socket 测试：注册项字节往返（目标用不可达的 `203.0.113.9:6881`，
  若实现真去 dial 会超时而不是假通过）、未注册回落直连回显、非 CONNECT 拒绝 `0x07`、
  非法 ATYP 拒绝 `0x08`、重复登记拒绝覆盖、splice 双向送达。
- 顺手修掉一个会把「明确拒绝」伪装成「网络断」的缺陷：原来先回拒绝码再关连接，
  但地址段尚未读完，Windows 回 RST，客户端只看到 `ConnectionReset`；
  改为**先读完地址段再判命令**。
- **照写的降级**：对端地址显示为 `127.0.0.1`（被引擎当本地 peer，不参与 PEX/通告、
  部分统计不计）；多一次用户态拷贝，未做大包压测前不写性能结论；注册项一次性。
- **v2.4.89 真引擎 e2e（回环）**：`EngineOptions.proxy_url` 已透传给 librqbit。
  两端独立 `RqbitEngine`，用 `cr_nat::tcp_punch` 在外部建真 TCP，以不可直连的
  `203.0.113.9:<port>` 登记进 `Bridge`；下载 1,048,576 B、落盘逐字节一致、
  做种方 `uploaded_bytes=1,048,576`、`served_registered=1`。
  负对照 `203.0.113.10:<port>` 不登记 → **0 B 下行**，排除回落直连假通过。
  证据：`tests/e2e/w54/reports/bridge_librqbit_e2e.json`。
- **未完成**：尚未接进 `wake_with_plan`；入向 `splice_to_listener` 仍只有单测；
  公网双侧打洞仍 `BLOCKED`。**不得说「BT 已支持公网打洞直连」**。

### 8.4 222 对照组：第一条真实 WAN 数据面证据

## 9. 第四轮补记（v2.4.90，2026-11-18 深夜）：打洞优先 / 中继兜底

> 本节是**当前状态**。`g2_claim=false`、`s6_status=not_run` 仍不变；全量回归
> **288 passed / 0 failed**（v2.4.90）。

### 9.1 做了什么

把「能打洞就打洞、打不了就中继」从口头设计变成**可执行且两端一致的判据**。
决策见 [ADR-022](../02-architecture/adr/ADR-022-punch-first-relay-fallback.md)。

- `cr-nat::punch_route`：纯状态机（std-only）。两阶段裁决 `Local → Commit`，
  只有「本端握手成功 ∧ 对端 Local ok ∧ 对端 Commit ok」才给 `Direct`。
- `cr-nat::punch_wire`：线格式 + 收发循环。裁决用既有 `RELAY`/`DELIVERED` 帧承载，
  **不新增帧类型、不动唤醒协议**（`cr-wake` 字段集合与 golden 未改）。
- `cr-core`：`nat.punch_route`（缺省 `false`）。关闭时 `proxy_url` 保持 `None`，
  既有部署逐字节不变。
- `coldrevived`：`PunchRouteState` 计数进 `/health`，常驻
  `relay_data_plane="not_implemented"`；新增 CLI `nat punch-route <对端id> [ip:port]`
  与 `nat punch-route-answer [ok]`（opt-in 才可用）。

### 9.2 证据

| 层 | 用例 | 结果 |
| :--- | :--- | :--- |
| 状态机 | 两端都 ok / 一端 ok / 都不 ok / Commit 先到 / nonce 不符 / 回显自己 | 12/12 通过 |
| 线格式（**真 `RelayServer`**） | 双方 ok → 两端 `Direct`；A ok/B 不 ok → 两端 `Relay`；都不 ok → `Relay`；带来源前缀负载被拒 | 5/5 通过 |
| 真引擎 e2e | Direct：登记 punched socket → `served_registered=1`、1 MiB 逐字节一致 | 通过 |
| 真引擎 e2e | Relay：不登记 → `served_registered=0`、1 MiB 逐字节一致 | 通过 |

机器可读：`tests/e2e/w55/reports/direct.json`、`tests/e2e/w55/reports/relay.json`
（`is_s6_evidence=false`、`g2_claim=false`、`s6_status=not_run`）。

**这些证据证明的是决策与交接闸门，不是公网可达性。**

### 9.3 实施期踩到的坑（写下来，避免复犯）

1. **`DELIVERED` 的 `payload` 不带来源 id**。服务端布局是 `frame.node = source`、
   `payload = 原始消息`。早前实现把来源 id 拼进负载，解出来 `side/nonce/stage` 全错位，
   而错位后 `observe()` 以 `NonceMismatch` 静默回落——表现成「对端不支持协商」，
   而不是报错。回归测试 `payload_with_node_prefix_is_rejected` 守着这条。
2. **`peer_addr()` 假阳性会传染到协商层**。socket 看着建起来了、实际上对端根本没收到，
   这时任何「本端 ok」都是假的。所以 `Direct` 必须要求**对端带 nonce 回帧**。
3. **回环 socket 转 tokio 前必须 `set_nonblocking(true)`**，否则 fd 注册错乱，
   `write` 立刻失败（`route_negotiated_e2e` 里踩过）。
4. **一端 Direct 一端 Relay 是双向黑洞**，不是「降级」：A 往 punched socket 发、
   B 在中继等，两侧日志都正常而数据一个字节不通。所以路由判定只有一份实现
   （`negotiate_route`），且测试强制断言两端相等。

### 9.4 仍未完成（口径不放宽）

1. **中继没有 BT 数据面**：`Route::Relay` 只表示「不登记 punched socket、保持引擎原有出向」。
   BT 流经中继转发是独立工作，先要过 ADR-014 的带宽预算。
2. **`wake_with_plan` 仍未创建/登记 punched socket**：本轮的接线是**可调用的控制面 + 计数 +
   opt-in 配置**，唤醒路径本身没改（改它需要先有对端 responder 与数据面，不能半边接线就说完成）。
3. **公网双侧打洞仍 `BLOCKED`**（ADR-018）；本轮不改变该结论。
4. 两个不同 NAT 经中继互达（§8.5 第 1 条）仍待用现有 A/221/222 或家宽机做一轮。

### 12.1 做了什么

### 12.2 先说坏消息：v2.4.92 的公网数据面是坏的

第一次按 W58 的方式跑，**1 MiB 一个字节都没到**，而看板全部「正常」：

| 观测 | 值 | 误导性 |
| :--- | :--- | :--- |
| 持有者 | `←引擎 1 049 585 B`、`splices_done=1` | 看起来完整供片 |
| 下载方 | `tunnels=1`、`bytes_relayed=1441` | 隧道「在」 |
| 中继 | `dropped` +98 / +224 | 真正的线索 |
| 下载 | `completedLength=0`，文件是 1 MiB 全零 | aria2 预分配 |

时间线（`tests/e2e/w59/reports/timeline.jsonl`，500 ms 一采）看得很清楚：
第 9 秒持有者已经写完 1 MiB，第 19 秒下载方才把 `bytes_relayed` 从 0 变成 1441。

**根因**：`RelayConn` 读帧用 `read_exact`，轮询读超时被归类成「本轮没有帧」直接返回，
但 `read_exact` 超时前**可能已消费半帧**，这些字节被丢弃；下一轮把帧体当帧头解析 →
「帧体超限」/解析失败 → 线程 `return Err` → 连接关闭 → 中继把后续帧计入 `dropped`。
加密路径 `SecureReader::recv` 同样如此，而公网中继**只走加密**。
LAN 上记录总是整块到达，W58 因此完全测不出来。

**修法**：`cr_nat::secure::fill_pending` 可续读缓冲（`read` 累积，超时保留缓冲），
明文/加密共用；隧道泵出错不再静默（打日志），`/health.data_plane` 新增 `tunnels_alive`。

   从 A 不可达，不是物理隔离。`nat_type=unknown`、`s6_status=not_run`。
2. **不证明打洞**：本轮 STUN 未产出映射（`public_udp_egress_ok=false`），

3. **控制面走 LAN**：advertise 与种子文件经 `192.168.1.222:17900` 取得，只有 BT 字节流进隧道。
4. **不是吞吐结论**：单次 1 MiB、无并发、无长稳；中继默认 512 KiB/s 数据令牌桶。
5. UDP 承载仍无数据面（无重传层），`relay_data_plane_udp="not_implemented"` 不变。

## 13. 第七轮补证据（2026-11-19）W60：真 STUN 分类下的打洞失败 → 中继接管

> 同版本 v2.4.93，**无代码改动**。`g2_claim=false`、`s6_status=not_run` 不变。

### 13.1 先纠正 W59 的一处结论

W59 报告里的 `nat_type=unknown` 是**报告的初始值**：`w59-run.sh` 只调用
advertise/peer/plan/wake，从来没调过 `nat probe`。所以「STUN 未产出映射」不是实测结论。
本轮补跑 `nat probe dedicated 3000`：

| 端 | 出口 | 两次目的地址的映射 | 分类 |
| :--- | :--- | :--- | :--- |
| A | `112.5.60.4` | `38576` / `38576` | `port-restricted-cone`（EIM 已实测） |
| 222 | `112.5.32.34` | `2053` / `2054` | `symmetric` |

### 13.2 真打洞（量具旁路）失败

用 `wake <file_hash> <infohash> stun-mapped` 强制直连候选（生产默认路径没有这个旁路）：

- 本侧另绑 socket，STUN 得映射 `112.5.60.4:38579`（与 probe 的 `:38576` 不同，符合预期）；
- 对 `112.5.32.34:2053` 真发 **2 个 punch 包**，并经中继让 222 回打了 **2 帧**；
- 结果 `punch_sent=2 acked=false peer_punched=false`，真实超时 **1203 ms**（os error 10060）。

这是机制性失败：symmetric NAT 到 A 的映射端口不可预知，STUN 看到的 `2053`
只是「到 STUN 服务器」的端口。之前 W58/W59 只试过通告里的私网 `192.168.34.222`，
这次才真正对公网映射打了一次。

### 13.3 生产自动路径中继接管

222 探测后如实自报 `relay-only`；生产 wake 先查中继得到 `skip_direct=true`，
直接选 relay：`ack_status=OK`、OPEN/OPENED 双向握手完成。
1 MiB `complete`、两端 md5 `b0e93e82…559e`；持有者 `→引擎 1,264 B / ←引擎 1,049,585 B`、
`splices_done=1`；下载方 `bytes_relayed=1,050,849`、`tunnels_alive=1`。

### 13.4 边界

1. 强制直连是**验收量具旁路**，生产按声明跳过；两者合起来说明「直连确实不可用，生产没有依赖它」。
2. 控制面（advertise / 种子）走 LAN；222 有 `192.168.1.222` 管理面别名，A 与 222 有 L2 通路，
   故**不是 NAT 可达性证据**。
3. 单次 1 MiB；`s6_status=not_run`、`evidence_valid_for_pass=false`、`g2_claim=false`。
4. 仍未完成只剩 **UDP 数据面**（无重传层）。

复现见 `tests/e2e/w60/README.md`；`python tests/e2e/w60/make_report.py` 18 条断言全过。

## 14. 第八轮（2026-11-19）v2.4.94：ADR-024 落地——UDP 承载上的 BT 数据面

> 所有者指令：「先出设计再实现」→ 审阅 ADR-024 提案后「按建议执行」。
> `g2_claim=false`、`s6_status=not_run` 不变；**默认承载仍是 `tcp`**，
> §11–§13（W58/W59/W60）的结论一条不改。

### 14.1 为什么做（不是性能问题）

W59/W60 已证明：**只要中继 TCP 承载可用，BT 数据面就能闭环**。但 ADR-020 §3.1 记录的那类
部署（腾讯云轻量 `119.29.150.254`：入向 TCP 在数据阶段被边缘注入伪造 RST，0/30 通过，
同期 UDP 全程正常）上，唤醒能走 UDP、BT 字节流无路可走。所以本轮补的是**部署覆盖面**。

### 14.2 四个阶段各做了什么

| 阶段 | 交付 | 关键判据 |
| :--- | :--- | :--- |
| 0 | UDP 字节预算（`--udp-data-rate` / `--udp-data-burst`，默认 512 KiB/s、2 MiB 突发） | 按 **`UdpKind::Data` 帧类型**计费，不能沿用「≤4096 B 绕过」——UDP DATA 全 ≤1152 B，那样等于免费；超限回 `UdpStatus::BandwidthLimited`（码 5 + 原因） |
| 1 | `cr_nat::relay_udp_stream`（std-only） | `"US"` 20 B 头 + 独立 app seq + 累积 ACK/64 位 SACK + `WINDOW=32` + RTO 200 ms→5 s + 3 dupACK 快重传；`STATUS` 永不滑窗 |
| 2 | `nat.data_plane_carrier`（默认 `tcp`） | 未收 `OPENED` 不登记隧道；持有方先拨本地引擎再回 `0xED`；**寻址与归属都要校验**（见 §14.4 第 6 条） |
| 3 | 两条证据 | 见 §14.3 |

### 14.3 证据（都在本机 `127.0.0.1`，一次干净运行）

**① 注入测试** `real_udp_relay_carries_1mib_under_loss_reorder_and_duplicate_injection`
（真 `UdpRelayServer` + 真 PSK/会话/转发；注入点在端点侧，中继保持生产行为、不加后门）：

| 方向 | seen | dropped | reordered | duplicated |
| :--- | ---: | ---: | ---: | ---: |
| DATA | 1220 | 56（4.6%） | 23（1.9%） | 11（0.9%） |
| ACK | 1175 | 57 | 20 | 14 |

结果：`retransmits=293`、`dup_dropped=248`、`max_inflight=32`、`max_incoming=31`、
交付字节精确 **1048576**（重复投递不增账）、`status_ignored=1175/1175`、耗时 **5.99 s**。

**② 真引擎** `udp_relay_frames_carry_real_librqbit_piece`（真 librqbit + SOCKS5 桥 + UDP 中继）：
`downloaded=1048576 finished=true`、持有者 `→引擎 1,264 B / ←引擎 1,049,586 B`、
中继 `deliver_out=1940`、`data_bytes_in=1,120,714`、`bandwidth_limited=0`。
同一测试文件里 TCP 那条用例并列跑，**同一把尺**。

### 14.4 边界（照写，不许放宽）

1. ①②两条证据都在本机回环，**不是**公网/跨 NAT 证据；③由 W61（§14.7）补齐。
2. v2.4.94 当时**没有**在 ADR-020 那类机器上复现，状态串曾是
   `udp-carrier-implemented-rst-unverified`；W61 后改为
   `udp-carrier-implemented-rst-path-verified`，`path` 仅限该主机该路径。
3. 无拥塞控制、无公平性量具：跨公网吞吐/与 TCP 共享瓶颈的表现一律不宣称。
4. 实施偏差：UDP 数据面未复用 `CD` magic + `TunnelMux` 分流（UDP DATA 已是独立会话，
   流内用 `"US"` 区分），OPEN 仍复用 ADR-023 的 23 B 编码。这条写进 ADR-024 §阶段 2，
   免得后来人以为两条承载走同一套分流代码。
5. 默认 `tcp`；未配 `data_plane_carrier` 的节点行为逐字节不变。
6. **实施期踩到的真坑（记下来）**：发起方一开始把 DATA 发到持有方的**节点 id**，
   而持有方的数据面会话注册在 `derive_session_id(node_id, b"cr-dp-v1")` 上——节点 id 那条
   会话是订阅/唤醒用的，OPEN 被订阅线程当唤醒帧丢掉，现场只表现为「3 s 超时回落直连」，
   看起来像对端没上线。所有单元/组件用例当时都是绿的，因为它们两端口径一致地「错」。
   修法：发起方改发派生 id；同时补两条红线——
   `udp_attach_registers_tunnel_when_holder_confirms`（正例，钉住寻址）与
   `recv_open_rejects_initiator_that_differs_from_observed_source`（冒名 OPEN 必拒）。
   **教训**：只有负例的握手测试等于没测，因为它可以因为「根本没连上」而通过。
