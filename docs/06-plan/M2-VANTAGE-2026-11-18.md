# 公网观测点实测记录（2026-11-18，第三轮）

> 前置：[ADR-019](../02-architecture/adr/ADR-019-public-vantage-nat-classification.md)（观测点设计与单 IP 边界）。
> 口径不变：**`g2_claim=false`、`s6_status=not_run`**。本文只记「量到了什么、凭什么」，
> 没量到的一律写在「BLOCKED」里，不折算成通过。

## 0. 环境

| 角色 | 地址 | 说明 |
| :--- | :--- | :--- |
| 观测点 | `119.29.150.254` | 腾讯云轻量，广州，Ubuntu 24.04，2C/2G/4Mbps，内网 `10.1.0.2`（**1:1 EIP**） |
| 出口 A | `112.5.60.4` | 家宽，Windows 前置机 `192.168.1.210` |
| 出口 B | `112.5.32.34` | 家宽，Ubuntu 23.04 `192.168.1.222`（与 A 不同线路） |

观测点启停：`/root/vantage.sh`（STUN 3478 主口 / 3479 备口 **+ UDP 中继 7101**，一次拉起），
中继 `/usr/local/bin/coldrevive-relay`，DHT `/usr/local/bin/coldrevive-dht`。
云防火墙**按端口放行**：UDP 3478-3479 / 6881 / 7101、TCP 22 / 7100 / 8443。
`7101/UDP` 在 v2.4.84 时未放行（§3.3 用抓包证明），**v2.4.85 所有人加规则后已复测通过（§3.4）**；
TCP `7100`/`8443` 即使放行，也在数据阶段被边缘注入 RST 拆掉（§3.1）。

## 1. 出口定性（本轮主结果）

| 出口 | 映射轴 | 过滤轴 | 定性 | 依据 |
| :--- | :--- | :--- | :--- | :--- |
| A `112.5.60.4` | EIM（3478/3479 同得 `:1951`） | `port-filtered`（双对照通过） | **port-restricted-cone** | 见下 |
| B `112.5.32.34` | APDM（`:2050` / `:2051`） | **不采用**（伪影） | **symmetric** | 见 §1.2 |

### 1.1 为什么 A 的结论这次站得住

三条独立证据同时成立才算数：

1. **服务端留痕**（`/tmp/stun.log`）：
   ```
   peer=112.5.60.4:1928 decision=AnsweredHere            ← 主口对照
   peer=112.5.60.4:1929 decision=AnsweredHere            ← 备口对照（独立 socket）
   peer=112.5.60.4:1930 decision=AnsweredFromPeerSocket  ← 服务端确实从 3479 回包
   peer=112.5.60.4:1931 decision=ChangeIpRejected        ← 420 已送达客户端
   ```
2. **客户端**：`change_port_answered=false`（服务端发了，客户端没收到）。
3. **对照 B 已通过**：客户端主动访问 3479 时能收到回包 → 备口入向可达。

「服务端发了」+「备口可达」+「客户端没收到」三者合起来才排除了旧代码那个歧义
（服务器忽略请求 vs NAT 丢弃）。**任何一条缺失，结论都只能是 `untested`。**

### 1.2 为什么 B 的过滤轴必须丢掉

B 的过滤探测同样返回 `outcome=port-filtered`。但 B 的映射是 APDM：
NAT 为目的端口 3479 另开了 `:2051`，服务端从 3479 回包落在**客户端从未用过的映射**上，
于是「收不到」。这是映射的副作用，不是过滤策略。

若按过滤轴定性，B 会得到 `port-restricted-cone`，与同一台机器的 `symmetric` 直接矛盾。
规则已固化为 `cr_nat::classify_two_axis`：**映射一旦随目的变化，过滤轴不参与定性**，
并有单测 `symmetric_mapping_makes_filter_axis_inadmissible` 守着。

| 节点 | `coldrevive-dht --serve 0.0.0.0:6881`，node id `04e9c1f9496e173b45c3ac6f800dc5cdbbac5f64` |
| A `--ping` | `ok=true`，`remote_id` 一致 |

## 3. 公网中继：原生端口 BLOCKED（仅隧道值，不充当原生指标）

| 观测 | 数据 |
| :--- | :--- |
| 221 → `7100` | `EHOSTUNREACH`，**2.4–2.9 ms**（同主机 `22` 端口 20.4 ms 正常） |
| 222 → `7100` | `EHOSTUNREACH`，**2.2 ms** |
| A → `7100` | TCP 握手完成、69 B 客户端 hello 正常到达；服务端 SYN-ACK 后 **150 µs** 出现 `ack` 号与本次连接不符的 RST |
| 换成纯 Python echo | 症状相同：服务端读到 `hello-from-A` 后自报 `Connection reset by peer` → **双向 RST** |
| 观测机主机安全 | 云镜 `YDService`/`YDLive` 已将 `coldrevive-*` 二进制与测试脚本标记 `Malware:113 report`（脚本 `mod 9`） |

**结论只到这一步**：7100 这条 TCP 路径被中间设备重置，与我们的帧协议无关（纯 echo 复现）。

### 3.1 8443 复测：不是端口问题，是「所有非 22 的入向 TCP」被注入 RST

所有者放行 TCP `8443` 后复测（2026-11-18 14:05–14:12），结论从「7100 不可用」修正为
**「此机器上除 22 以外的入向 TCP 一律被 RST 拆掉」**。

**报文级证据**（`tcpdump -ni eth0 -vv`，服务端视角）：

| 时间（相对） | TTL | 方向 | 内容 |
| :--- | :--- | :--- | :--- |
| +0 µs | **116** | 客户端 → 服务端 | `[S]`，`tos 0x68` |
| +46 µs | 64 | 服务端 → 客户端 | `[S.]`（本机内核回的，非代理） |
| **+669 µs** | **215** | 声称来自客户端 | `[R.]`，`ack 610780543`（服务端 ISN 是 `3684186753`） |
| +27.8 ms | **116** | 客户端 → 服务端 | `[.]` 真实 ACK |
| +28.0 ms | **116** | 客户端 → 服务端 | `[P.]` 69 B（中继 hello） |
| +33.9 ms | 64 | 服务端 → 客户端 | `[P.]` 65 B（中继 hello 应答） |
| +55.5 ms | **116** | 客户端 → 服务端 | `[R]` 客户端自己发的 RST |

判据只有一条，但足够硬：**同一台客户端的所有真实报文 TTL 恒为 116，而那条 RST 的 TTL 是 215**。
TTL 只能沿路径单调递减，不可能出现「同一个发送者、更近的跳数」。
所以那条 RST 是**伪造的**，且注入点距服务器仅 **669 µs**（不可能来自 12.5 ms 单程的客户端）。

**第三次、第四次的 TTL 分别是 65 和 169**（同一客户端同一路径，真实报文永远是 116）。
同一个伪造者三次给出三个不同的 TTL —— **这是刻意的 TTL 随机化**，用来让伪造包不呈现固定指纹。
换句话说，这个中间设备不仅会造假，还在主动规避取证。真实客户端的 TTL 由自身栈决定，不可能随机。

**排除项**（逐条实测，不留「可能」）：

| 假设 | 实测 | 结论 |
| :--- | :--- | :--- |
| 是 7100 端口被针对 | 8443 表现完全一致 | 否 |
| 是我们的帧协议/PSK 握手被识别 | 纯 Python echo、`hello-8443`、HTTP 请求全部同样被拆 | 否 |
| 是协议特征检测（DPI） | SSH banner、真 TLS ClientHello、64 B 随机串，四种开头全部 `RESET`（2.4–3.3 ms） | 否 |
| 是客户端本机（杀软/防火墙/代理） | Defender 为唯一 AV、专用/公用配置文件均关闭、WinHTTP 直连；`Sense` 已停 | 否 |
| 是云镜（主机安全）在机器内部拦 | ① 机内 `iptables`/`nft` 无相关规则、`tc` 无过滤器、`lsmod` 无厂商模块、云镜日志只有登录检测；② **停机对照实验**：持续 `kill -9` 压制 `YDService`/`YDLive`，测试全程 `pgrep -c -x` 均为 **0/0**，8443 **仍被拆**，伪造 RST 照旧出现（TTL **169**，晚于 SYN-ACK **270 µs**，`ack` 仍为无关值） | **已证否** |
| 是「空闲也会被拆」 | 只建连不发数据，**存活 8 s 无 RST**；发 1 字节即被拆 | 否 |
| 是云防火墙规则没生效 | SYN 能到主机、主机能回 SYN-ACK（46 µs） | 规则**已生效** |
| 是服务器自身 | 机器 → 自己的 EIP（`119.29.150.254:8443`）回环直连，`echo` 正常往返 1.0 ms | 否 |

即：**放行规则是生效的，但连接一进入数据阶段就被外部注入的 RST 拆掉**，注入点在服务器侧边缘。
这台机器是腾讯云轻量，同一台机器的 UDP（3478/3479/6881）与 TCP 22 全程正常，
所以问题边界明确落在「非 22 的入向 TCP」上，不扩大成「中继不可用」。

### 3.2 在可用路径上量到的 WAN 往返（经 SSH 隧道，标注清楚）

`22` 是唯一可用的 TCP 端口，于是用 `ssh -L` 把本机 `27100` 转发到观测机的
`127.0.0.1:17100`（中继只绑回环），再从本机跑 `coldrevive-relaybench`：

| 指标 | 数值（200 轮，64 B 载荷） |
| :--- | :--- |
| 送达 / 丢失 | **200 / 200，0.00 %** |
| p50 / p90 / p99 | **44.27 / 46.25 / 47.33 ms** |
| min / max / mean | 38.06 / 60.71 / 44.14 ms |
| 同路径 ICMP 基线 | 25–27 ms（均值 25 ms） |

**这组数字能说明什么、不能说明什么**（避免被当成原生中继指标）：

- 能说明：中继的帧路由与 PSK 握手在真实 WAN 路径上**功能正确、零丢失**，
  且 `44.27 − 25 ≈ 19 ms` 的差额主要来自 SSH 通道自身的往返与中继一跳处理，量级合理。
- 不能说明：**原生 TCP 中继在公网可用**。原生端口仍然被 RST 拆掉，
  所以这组数只能记为「经 SSH 隧道的真实网络往返」，`evidence_scope` 仍是
  `real-network-roundtrip`，但**端口可用性判据不因此改变，仍是 BLOCKED**。
- v2.4.80 的 LAN 数字（A p50 0.82 ms / 222 p50 0.59 ms）继续作为**中继自身开销**的基线；
  本轮数字是「中继 + SSH + WAN」的合成值，两者不可互相替代。

### 3.3 UDP 承载：换掉被掐的那一层，中继在原生公网路径上跑通（W3.14 / v2.4.84）

§3.1 的结论是「非 22 的入向 TCP 在数据阶段被边缘注入 RST」，那么正确的下一步不是
再要一个 TCP 端口，而是**换承载层**——同一台机器的入向 UDP 一直是好的（3478/3479/6881）。

**先确认 UDP 是「按端口放行」而不是「全放行」**（否则下面的数字会被误读成「UDP 随便用」）：

| 观测 | 结果 | 结论 |
| :--- | :--- | :--- |
| A → `119.29.150.254:7101/UDP` 发 `HELLO`，服务器 `tcpdump -ni eth0 -U "udp port 7101"` | **`0 packets captured`** | 报文没到 NIC |
| 同一时刻 A → `119.29.150.254:3478/UDP` 的 STUN Binding | 正常应答，`public_udp_egress_ok=true`，映射 `112.5.60.4:5287` | A 的 UDP 出向没问题 |
| `7101` 是否在中继日志里被拒 | 否：`datagrams=0`、`mac_fail=0` | 不是密钥/协议问题 |

即：**云防火墙对 UDP 也是按端口放行的**。本轮为避免再动一次防火墙规则，
临时让中继占用已放行的 `6881/UDP`（原 DHT 端口，测试期间 DHT 下线约 15 分钟，测完已放回）。
所有者在随后一轮加了一条 `UDP 7101` 规则，专用端口复测见 §3.4。

**测量（三个口径，全部 0 丢包）**：

| 口径 | 轮数 / 载荷 | 丢失 | p50 | p90 | p99 | 抖动（相邻差均值） |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 同机双 socket（A、B 都在 `192.168.1.210`） | 50 / 200 B | **0** | 49.39 ms | 50.51 ms | 52.76 ms | 0.103 ms |
| 同上，加长样本 | 200 / 200 B | **0** | 52.93 ms | 53.80 ms | 54.55 ms | 0.021 ms |
| 同上，接近上限的载荷 | 100 / 1100 B | **0** | 49.63 ms | 50.80 ms | 52.44 ms | 0.083 ms |
| **双主机**（A=`210`，B=`221`，同一出口 `112.5.60.4`） | 200 / 200 B | **0** | **42.68 ms** | 43.35 ms | 43.62 ms | 0.016 ms |

**跨主机那一轮的三方对账**（三处独立计数，缺口必须为 0，否则就是「只报成功不报丢失」）：

| 观测点 | 读数 |
| :--- | :--- |
| A 侧（`coldrevive-relaybench --udp --udp-remote-echo`） | `rounds=200`、`received=200`、`lost=0`、`status_forwarded=200` |
| B 侧（221 上的 `--udp-echo`，独立进程独立 socket） | `delivered_in=200`、`echoed_out=200`、`bytes_in=40000`（= 200 × 200 B，逐字节相符） |
| 中继计数器增量（`/root/udp_stats.json`） | `datagrams +403`（2×HELLO + 400×DATA + 1×BYE）、`data_in +400`、`deliver_out +400`、`status_out +400`、`mac_fail 0`、`replay 0`、`target_absent 0` |

`data_in +400` 正好等于「A 发 200 + B 回 200」：中继既没有重复投递，也没有少转一帧。

**与 ICMP 的一致性**（说明这 40–50 ms 是路，不是中继）：同路径 ICMP 12 包 **0 丢、25–26 ms 往返**。
一次中继往返由 4 段单程组成（A→中继→B→中继→A），理论值 ≈ 2 × ICMP 往返 = **50 ms**；
实测 p50 `42.68`（跨主机）/ `52.93`（同机）正落在这一区间，差额含两次用户态转发与调度。

**这条证据能说明什么、不能说明什么**：

- 能说明：UDP 承载的**帧转发、PSK 逐报文鉴权、会话注册/注销、拒绝带原因**在真实公网路径上
  全部工作，零丢失，且两端的独立计数与中继计数逐条对得上。
- 不能说明：**原生 TCP 中继可用**——§3.1 的 BLOCKED 结论不变，UDP 只是绕开了被掐的那一层。
- 不能说明：**两个不同 NAT 同时经中继互达**。A 在 `210`、B 在 `221`，但 `ip route` 与
  `curl ifconfig.me` 都显示二者的公网出口同为 `112.5.60.4`——这是「两台主机、一个 NAT」，
  比同机双 socket 强（不同源端口、不同进程、不同主机），但**不是两个 NAT**。
  真正需要 222 或另一条线路，本轮没有条件，照写为未测。
- 不能说明：UDP 可靠。`STATUS=forwarded` 只表示「中继转出去了」，不表示对端应用收到；
  本项目不在 UDP 上做重传，丢包如实计入 `lost`。

### 3.4 专用端口 `7101/UDP`：规则生效，DHT 不再被借用（v2.4.85）

§3.3 的临时做法是「借 6881」。所有者加了一条 `UDP 7101` 放行规则后，**先用抓包确认规则真的生效**，
再在专用口上重测——否则「通了」可能只是又一次借用了别的已放行端口。

| 观测 | 结果 |
| :--- | :--- |
| 中继 `--udp-listen 0.0.0.0:7101` 启动 | `ss -lnup` 见 `0.0.0.0:7101`；日志 `最大负载 1168 字节` |
| 服务器 `tcpdump -ni eth0 -U "udp port 7101"`（3 轮探测期间） | **26 个包**，首包 `112.5.60.4.5498 > 10.1.0.2.7101: UDP, length 64`，逐条有回程 |
| 对照：同一抓包口径在规则加入前（§3.3） | **`0 packets captured`** |
| 端口冲突 | 无：`6881/UDP` 复归 DHT（`coldrevive-dht --serve 0.0.0.0:6881` 始终在跑，本轮未下线） |

「0 包 → 26 包」是这条规则生效的**直接证据**，不需要推断。

**跨主机测量（A=`192.168.1.210`，B=`192.168.1.221`，中继 `119.29.150.254:7101`，全部 0 丢包）**：

| 轮数 / 载荷 | 丢失 | p50 | p90 | p99 | 抖动（相邻差均值） |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 500 / 200 B | **0** | 48.96 ms | 49.63 ms | 52.87 ms | 0.030 ms |
| 100 / 1100 B | **0** | 34.21 ms | 35.09 ms | 36.10 ms | 0.028 ms |

**载荷大小不影响 RTT —— 用交替实验排除，而不是靠单次样本下结论**。
上面两个样本看似「1100 B 比 200 B 快 15 ms」，于是同路径交替跑四组（各 60 轮）：

| 顺序 | 载荷 | p50 |
| :--- | :--- | :--- |
| 1 | 200 B | 33.95 ms |
| 2 | 1100 B | 46.59 ms |
| 3 | 200 B | 43.18 ms |
| 4 | 1100 B | 42.75 ms |

大小顺序被打乱 ⇒ **载荷与 RTT 无关**。同一路径多次样本的 p50 落在 **34–52 ms**，
所以本报告**不记任何单一 p50 作为「端口性能」**，只记区间。
未证实的推测（**不作结论**）：每个 bench 进程用新的源端口 ⇒ 新的 NAT 映射 ⇒
运营商侧按五元组散列选路，可能落在不同路径上；要证实需要按源端口做逐跳对比，本轮没做。

**三方对账（840 轮，三处独立计数，逐字节精确）**：

| 观测点 | 读数 | 校验 |
| :--- | :--- | :--- |
| A 侧 | `rounds=840`（500+100+4×60）、`received=840`、`lost=0`、`status_forwarded=840` | — |
| B 侧（221 独立进程） | `delivered_in=840`、`echoed_out=840`、`bytes_in=366000` | `= 620×200 + 220×1100`，**逐字节相符** |
| 中继 | `data_in=1680`、`deliver_out=1680`、`status_out=1680` | `= 2×840`（A→B 与 B→A 各一份），无重复投递、无漏转 |
| 中继字节 | `bytes_in=867232` | `= 1240×280 + 440×1180 + 7×64(HELLO) + 6×64(BYE)`，**精确相等** |
| 健康计数 | `mac_fail=0`、`replay=0`、`target_absent=0`、`too_big=0`、`bad_format=0` | 无丢弃、无重放、无格式错 |

**同时纠正 v2.4.84 的一处错误结论（MTU）**：v2.4.84 写「64 B 头 + 1200 B 负载 = 1264 B，
留在 1280 的 IPv6 最小 MTU 之内」——**漏算了 IPv6 的 40 B IP 头 + 8 B UDP 头**，
`1264 + 48 = 1312 > 1280`，这句话是假的。
本版把上限改为 **1168 B**（`64 + 1168 = 1232`，`1232 + 48 = 1280` 正好填满），
并加单测 `max_datagram_fits_ipv6_min_mtu` 把「不分片」这一定性约束钉死；
1100 B 载荷（线上 1180 B）在此上限内，上表就是用它测的。

**仍不能说明的**：A/B 同出口 `112.5.60.4`，还是「两台主机、一个 NAT」，**不是两个 NAT**；
UDP 无重传，`forwarded ≠ 对端收到`；§3.1 的原生 TCP BLOCKED 结论不变。
专用端口解决的是「借端口」，不是「TCP 被掐」。
