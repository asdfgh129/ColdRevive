## 1. 第 1 点：公平性在测什么，为什么 78/80 还算 FAIL？

### 1.1 实验设置（用人话讲）

在 221 这台机器上用两个网络命名空间造出两条虚拟线路，让**两条数据流同时通过同一个中继**
抢带宽。两种线路形状：

- **L1**：16 Mbit/s、20 ms 延迟、2 ms 抖动 —— 相当于比较宽的通道；
- **L2**：8 Mbit/s、50 ms 延迟、5 ms 抖动 —— 相当于更窄、更卡、抖动更大的通道。

四种模式（arm）：

- `cc_off`：关掉端侧拥塞控制，作为「量具是否偏袒某一条流」的对照；
- `cc_on`：打开 AIMD + RTT 超时重传；
- `cc_paced`：在 `cc_on` 基础上再加发送整形；
- `cc_on_per_session_cap`：打开中继侧每会话字节桶，用来区分「中继限流」与「端侧退让」。

### 1.2 判据（事先写死，采样本之前已登记）

`tests/fixtures/g2-fairness-thresholds.toml`，sha256 `0671a173…` 未改：

- 预热 3 秒，正式采样 10 秒；
- 每种模式每轮各跑 10 轮；
- 每条流实际收到的字节占比必须在 **45%–55%**；
- Jain 公平指数 ≥ **0.95**；
- **每一轮都要达标**，平均达标或中位数达标都不算（防止「9 轮很好、1 轮很糟」被平均掉）。

### 1.3 结果（翻译成人话）

| 线路 | 模式 | 结果 | 说明 |
|---|---|---|---|
| L1 | 四种模式 | 10/10 全过 | 宽通道下没问题 |
| L2 | `cc_off` | 10/10 全过 | 说明量具本身没有偏袒某条流 |
| L2 | `cc_on_per_session_cap` | 10/10 全过 | 说明中继限流不是失败原因 |
| L2 | `cc_on` | **9/10** | 第 7 轮 0.430 / 0.570 |
| L2 | `cc_paced` | **9/10** | 第 8 轮 0.433 / 0.567 |

所以总共 80 轮里 78 轮达标，但判据是「每种模式 10 轮全达标」，
L2 的 `cc_on` 和 `cc_paced` 各差 1 轮，**整体只能写 FAIL**。

`r = −0.706` 不是「70% 通过率」，而是相关系数：
「两条流丢包数差得越多，字节份额离 50% 越远」这个倾向比较强。
两轮失败恰好是丢包不对称最大的轮次；中继 shaping/dropped/limited 全为 0，
`cc_off` 的 20 轮都落在 0.499–0.502，说明不是量具偏心。

### 1.4 为什么不改参数重跑

AIMD 的 β（丢包后窗口减半系数）写死在探针 `main.rs:189`，当前是 0.5。
把它改成 0.7 再重跑，等于**看到结果后改规则**，违反「判据先于样本」。
所以原样保留 80 轮，既不删失败轮，也不靠多跑几次碰运气。

**所有者决定（2026-11-25 09:28，17:15 书面化）**：这两轮偏差在可接受范围内，先记录在案、
本版跳过，不调 β、不改阈值、不改判据；**下一版**再重新调整测试——
必须先以新时间戳 + 新 sha 登记新判据，再采集新样本。
已写成正式书面例外：`docs/06-plan/G2-FAIRNESS-EXCEPTION-2026-11-25.md`（DOC-33 / **EX-1**），
后果逐条写死为 C1–C6（判定仍是 FAIL、结论强度上限、三条失效条件、下一版义务、正负措辞、残留风险 R-16）。
机器落点 `g2-spike-verdicts.toml` → `[fairness_exception]`。
**判定没有因此变成 PASS**：`aggregation = all_rounds_must_pass` 之下，78/80 就是 FAIL，
例外改变的是「这个 FAIL 怎么被接受、影响哪些表述」，不是结果本身。

## 2. 第 2 点：真实 Mainline DHT 到底过没过？

**答：这项组件测试过了，但不是 G2 过了。**

原来的障碍是引导节点不给 token（`token_len=0`）或超时。这次换了做法：

1. 用 `coldrevive-dht --walk` 从真实公网节点找到活节点；
2. 向真实路由节点拿 **真 token**（不是伪造）；
3. 发 announce，并确认收到 ACK；
4. 用**新的** get_peers RPC，在 **2 个不同公网节点**上查到 `112.5.60.4:17800`；
5. 新增 `--announce-seed` 直接调用守护进程 FR-18 用的 `announce_active_seed`，
   对真节点返回 `announced_verified`（`token_len=4`、`peer_verified=true`）。

判据 `walk_answered` / `token_issued` / `announce_accepted` /
`fresh_rpc_recheck` / `multi_node_placement` 全部 met。

**补充：守护进程自动运行（2026-11-25）**：在 221 上以 `dht.enabled=true`、
IPv4 公网节点作 bootstrap 跑 10 分钟，20 次 `/health.dht` 采样显示

**边界**：这是单次 CLI + 10 分钟有界 daemon 窗口的组件级真实网络证据。

## 3. 第 3 点：守护进程多样种逐出，是出了什么问题吗？

**答：不是出了问题，是这个规则以前缺一份用当前构建跑出来的证据，现已补齐。**

规则：配置 `max_active_seeds = 1` 时，索引里可以有很多个文件，但**同时处于热做种状态的只能有 1 个**。
要验的是：

- 第一个文件被唤醒时，确实开始做种（`seed_active=1`）；
- 第二个不同 infohash 的文件被唤醒时，它会唤醒**自己的**做种任务；
- 旧任务被逐出（`evictions=1`），但活跃数始终 ≤ 1；
- 守护进程重启后索引与状态仍正确。

当前 release 构建跑 `tests/e2e/p0/run_p0.py`：**77/77 PASS**，其中 FR-10 关键项
两个不同 infohash 的真 BT 握手、cap=1、`evictions=1`、
`second_infohash_wakes_its_own_task`、`wake_count_never_exceeds_cap` 全部通过。

**边界**：这是本机回环双进程测试，不是公网 NAT 证据。它证明的是「逐出规则正确」，
不是「公网可达」。

**S6 语义复核材料（本次补入）**：S6 在 2026-11-17 已由 G0 判 `pass`，
但 `verdict_kind=closed_with_exceptions`，不是无例外通过。机器字段
`s6_status=not_run` 是**有意分层**，不是漏改。复核触发条件是「M4 或 ≥4 个不同真实出口」，
出口数已达 4（`112.5.60.4`、`112.5.32.34`、`82.157.68.159`、`119.29.150.254`），
**数量条件成立**；类别在 2026-11-25 15:38 给广州那台放通入向 UDP 后从 2 类升到 **3 类**
（`full-cone`、`port-restricted-cone`、`symmetric`），仍缺 `restricted-cone`、`CGNAT`。
**该复审已于 2026-11-25 执行完毕**（ADR-016 §复审记录 R1）：所有者取第 ① 项，
维持 eMule 式可达语义、不恢复完整类别矩阵，触发条件改为「≥4 出口且 ≥3 类别」双条件。
S6 判定引用的三份报告原件位于 gitignored 的 `tests/spikes/s6/reports/`，
2026-11-25 已逐字节归档到 `tests/ARCHIVE/evidence/s6-verdict-20261117/`（含 sha256 清单、
`.gitattributes` 锁字节），clone 后可复核；原件目录仍不入库。
复核时只允许表述为「按 eMule 语义结案、带已知限制」；
不得写成「NAT 矩阵通过」「G2 达标」或任何可达率百分比。

### 4.5 绕过打洞、直接拨 B 的公网映射：网络通，应用层不通

既然 B 侧本来就有静态映射 `112.5.32.34:19920 → 192.168.34.222:19920`，
本轮改测「不猜端口、直接拨这个已知公网地址」。结论分两层，必须分开说：

**网络层 PASS（两个独立客户端一致）**

| 客户端 | 结果 |
|---|---|
| A / 221（出口 `112.5.60.4`） | TCP 三次握手完成，B 侧抓包可见 SYN/SYN-ACK/ACK |
| 云观测机 `82.157.68.159` | 同样完成三次握手 |

B 上 `tcpdump` 各记录 8 个包，说明静态 DNAT 入向确实把连接送到了 `222:19920`。
证据 `bt-handshake-direct-19920-two-client-20261125.json`。

**应用层 BLOCKED**：两个客户端各自发出 68 字节标准 BitTorrent 握手后，
B 的引擎先 ACK 这 68 字节，紧接着发 **FIN**（不是 RST），从头到尾没有回握手。
两次结果完全一致，所以不是偶发丢包。

**根因（已定位到代码）**：B 的种子处于 `state=cold`。
冷态是 `idle::sleep_hot_seeds()` 调 `pause_seed()` 把引擎里的种子**暂停**了，
被暂停的 torrent 不会接入向 peer，于是握手被读到后直接关连接。
这也解释了为什么中继那条能过：中继路径会先 `nat wake` 真正激活持有者，而直连路径没有任何环节去激活。

**加热路径当前是断的**（三组对照全部归档）：

1. 直接 `nat wake` → `无活动 NAT 计划，先 nat probe / nat peer`，种子仍 cold；
2. 补 `nat peer` + `nat probe` 后 `nat wake` → `ok=true` 但 `path=relay`，
   种子仍 cold，握手仍被 FIN；
3. 原因是 B 视角下「对端无外部映射证据，仅私网直连候选」，
   wake 走了中继，而中继不负责激活**本机**的种子。

**另一个独立缺陷**：下载侧拿不到公网 peer。
A 的 aria2 兼容接口一直 `connections=0`。**更正 v2.4.129 的表述**：
旧逻辑不是「返回空 peer 列表」，而是把**对端私网地址**（`192.168.34.222:19920`）
回给了私网请求方。A 在 `192.168.1.0/24`，那个地址对它不可路由，
所以引擎根本拨不出去——即便种子是热的也一样。

### 4.6 v2.4.130：把「下发公网 endpoint」这一条改掉了，结果如下

改动只有一处：`tracker_endpoint_for()` 现在先判断「请求方与对端是否同 /24」。
同网段照旧给局域网地址（更快）；跨网段且有真实公网映射（公网 IPv4 且
`internal_port == bt_port`）时下发该公网地址；没有真实映射仍退回私网地址，不伪造可达性。
`Relay` 会合地址不参与这条路径，公网请求方的行为逐字节不变。

现场结果（证据 `tracker-public-endpoint-dial-20261125.json`）：

| 检查 | 结果 |
|---|---|
| A 向 B 的 `/announce` 拿到的 peer | `112.5.32.34:19920`（旧值 `192.168.34.222:19920`） |
| A 的引擎是否真的拨出 | **是**：B 侧抓到 `112.5.60.4.38695 > 192.168.34.222.19920: [S]` |
| 是否发出真 BT 握手 | **是**：同一连接随后 `length 68`（标准握手） |
| 字节是否到达 | **否**：60 秒内 `completed=0`、`download_speed=0` |
| A 落地文件 | 长度 1048576 B，但 md5 `b6d81b36…`＝1 MiB 全零，属引擎预分配，零字节传输 |

**结论：控制面通了，数据面还卡在第 (a) 条**——B 的引擎收到 68 字节握手后不回，
`seed_active` 全程为 0，仍是「冷种子被 pause 住不接入向 peer」。
这一段必须改代码（入向握手唤醒 / 通告期间不得暂停），本版按你的指示只做了第 (b) 条。

**所以「直连」这件事的真实成本**：不是改 CPE、不是重做 DNAT。第 (b) 条已落地并验证；
剩余只有第 (a) 条这一处行为变更，动的是 FR-14 的休眠语义，需要你先定语义我才能改。

### 4.7 v2.4.131：你选了「握手命中即唤醒」，已改并实测到 md5 一致

按你的决定实现，**没有新造协议**：librqbit 没有握手回调，观测入向握手只能在外围读
68 字节，那正是 FR-11 的 `cr-guard`。本轮把它变成可部署的唤醒路径，并修掉两处
只会在现场出现的缺陷：

1. 代理原来跟着 `engine.listen` 绑地址。部署里为把 LAN 的 `bt_port` 让给打洞 socket，
   会写 `engine.listen=127.0.0.1:<bt_port>`——于是代理只绑回环，DNAT 过来的握手
   永远进不了唤醒逻辑。现在只要配了外部映射，代理一律绑 `0.0.0.0:bt_port`。
2. `activate` 返回 Ok 不代表引擎已能处理握手。立刻把那 68 字节补回去，引擎照样 FIN，
   和「没唤醒」长得一样。现在有界等引擎自报 `HOT`（≤3 s）再 splice。

配置写法：`"engine": {"wake_on_handshake": true}`（与 `guard_handshake` 同义）。
默认仍关闭——代理会长期占住 `bt_port`，与同端口打洞互斥，这是逐节点的取舍。

实测（证据 `bt-wake-on-handshake-lan-20261125.json`，LAN 直拨 A`192.168.1.221` →
B`192.168.1.222:19920`）：

| 检查 | 结果 |
|---|---|
| 拨号前 B 种子 | `state=cold`、`seed_active=0` |
| B 监听 | 代理 `0.0.0.0:19920` + 引擎 `127.0.0.1:43693`（绑定修复生效） |
| B 抓包 | SYN → `length 68` 入 → `length 177` 出（引擎回了握手+位图） |
| `/health.guard` | `handshakes=1, woken=1, missed=0` |
| 拨号后 B 种子 | `state=hot`（**全程没有调用 `nat wake`**，是握手本身叫醒的） |
| A 侧下载 | `status=complete`、`1048576 B`、约 4 秒 |
| 落地 md5 | `6209e962f3b26a13c9ec1ae70fd78e10` = B 种子文件，一致 |

**这一轮补上了公网变体，并且它过了**（证据 `bt-wake-on-handshake-public-20261125.json`）：

| 检查 | 结果 |
|---|---|
| 两个独立公网观测机连 `112.5.32.34:19920` | `82.157.68.159`、`119.29.150.254` 都完成 TCP 握手，B 的 `ens160` 抓到各自 SYN + SYN/ACK |
| A 实际拨号 | `112.5.60.4:40508 → 192.168.34.222:19920`（`112.5.60.4` 就是 221 的出口） |
| B 抓包 | SYN → `length 68` 入 → `length 177` 出 → `length 98` 入（真 BT 握手 + 位图，跨公网） |
| `/health.guard` | `handshakes=1, woken=1, missed=0` |
| 拨号后 B 种子 | `cold` → `hot`，**未调用 `nat wake`** |
| A 侧下载 | `status=complete`、`1048576 B` |
| 落地 md5 | `6209e962f3b26a13c9ec1ae70fd78e10` 一致 |

**更正上一版的误判**：上一版说「CPE 映射已撤，两个观测机都收到 RST」是错的。真实原因是
当时 B 的 `engine.listen=127.0.0.1:19920` 且 guard 未启用，`0.0.0.0:19920` 没有任何监听，
RST 由 222 自己的内核发出；CPE 映射自始至终都在。判据错误已归档为一条 `INFO` 更正记录。
一般化教训：**DNAT 端口回 RST 不能证明映射没了**，先确认后端端口真的有人 listen。
（另一个同源坑：本机在 `192.168.1.0/24` 内测 `112.5.60.4` 会因家宽不支持 hairpin 失败，
公网可达性必须从外部观测机测。）
