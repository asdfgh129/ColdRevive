# ADR-020 中继的 UDP 承载（换层而不是换端口）

## 状态

已采纳（2026-11-18）。实现：`cr-nat::relay_udp`；CLI：`coldrevive-relay --udp-listen`、
`coldrevive-relaybench --udp / --udp-echo / --udp-remote-echo`。

## 背景：TCP 路被掐死，而 UDP 是好的

2026-11-18 在腾讯云轻量 `119.29.150.254` 上测得：**除 `22` 外的入向 TCP 在建连后被边缘注入伪造 RST**
（`7100`、`8443` 一致；伪造包 TTL 随机化 215/65/169，而真实客户端恒为 116；
停掉主机安全组件后依旧；详见 [M2-VANTAGE](../../06-plan/M2-VANTAGE-2026-11-18.md) §3.1）。
同一台机器的入向 UDP（`3478`/`3479`/`6881`）全程正常。

### 复盘对照（2026-11-18 17:5x）：是这台机器的策略，不是普遍规律

为了区分「该云主机边缘策略」和「所有入向 TCP 都不行」，在腾讯云和 222 的**同一端口 7100** 上
各起纯 TCP 回显，从 A 侧同口径探测：

| 对端 | 建连 | 数据阶段 | 抓包证据 |
| :--- | :--- | :--- | :--- |
| 腾讯云 `119.29.150.254:7100` | ✅ | ❌ 13/64/128/256/512/1024 B 各 5 次，**0/30 通过** | eth0 抓到大量伪造 RST，TTL **44/67/82/95/132/142/208/215/217** 随机；真实客户端恒 116，服务端 64 |
| 222 `112.5.32.34:7100` | ✅ | ✅ 中继 30/30 @256 B（p50 6.03 ms）、30/30 @1200 B（p50 9.44 ms） | ens160 同期抓 RST **0 个** |

结论：伪造 RST 是**该云主机的边缘策略**，不是普遍现象；本 ADR 的「换承载层」只在这条路径上必要。
另有一次异常：17:54:51 一次 13 B 回显成功（报文字只有真实 TTL 116/64），随后同载荷连测全部失败。
**单次成功也不能推翻结论，判据必须多轮。**

于是有两条路可走：

1. 再要一个 TCP 端口（`443` 等），赌边缘策略对它不同——**这是赌博**：§3.1 已证明它不看端口、不看协议内容；
2. 换承载层，把中继搬到 UDP 上——代价是失去 TCP 的可靠性语义。

选 2。理由不是「UDP 更快」，而是：**在被掐的是 TCP 这一层时，唯一确定可用的层是 UDP**。

## 决策

### 1. UDP 是一套独立的线缆格式，不是 TCP 帧的搬运

复用 `relay::FrameKind` 的编号会让读者以为两种帧可以互转。实际上：

```
0..4   "CRU1"   4..5 kind   5 flags   6..8 len
8..24  session(16)   24..32 seq(8)   32..64 HMAC-SHA256   64.. payload
```

固定头 64 B + 负载上限 1168 B = **1232 B UDP 负载**；加 IPv6 的 40 B IP 头 + 8 B UDP 头正好 1280，
即**恰好填满 IPv6 最小 MTU、不需要分片**。帧类型独立编号（`0x01` HELLO … `0x09` REJECT）。

> 更正（v2.4.85）：本 ADR 初版写「1200 B 负载 = 1264 B，仍在 1280 之内」，
> 漏算 IPv6 + UDP 的 48 B 头（`1264 + 48 = 1312 > 1280`），该说法是错的。
> 上限随之从 1200 改为 **1168**，并由单测 `max_datagram_fits_ipv6_min_mtu` 钉住。

### 2. 每个报文都要 PSK 的 HMAC，且回程不大于来程

UDP 没有握手，一个开放的中继会被当作反射/放大跳板。三道约束同时成立才允许公网部署：

- 逐报文 `HMAC-SHA256(psk, 头 || 负载)`，校验失败静默丢弃（计 `mac_fail`，不回声）；
- 回程字节数**不大于**来程（`PONG` 16 B、`STATUS` 9 B），放大系数 < 1；
- `seq` 单调 + 64 位滑窗抗重放（接受乱序，只丢真重复）；
- 未配 PSK 时只允许绑回环（策略在二进制里，与 TCP 侧同一条闸门）。

### 3. 拒绝必须带原因，状态必须可区分

沿用 TCP 侧的教训（`FrameKind::Reject`）：只丢包不改声，运维会去查网络。

| 帧 | 语义 |
| :--- | :--- |
| `HELLO` → `HELLO_ACK` | 注册；被拒时回 `REJECT` + UTF-8 原因（会话表满 / 单 IP 超限 / 未配密钥） |
| `DATA` → `DELIVER` | 转发；发送方另外收到 `STATUS` |
| `STATUS` | `forwarded` / `target_absent` / `rate_limited` / `too_big` / `not_registered` |

`target_absent`（对端没注册）与「没收到 STATUS」（路径丢了）是**两种排障方向**，不允许合并。

### 4. 不在 UDP 上做重传

UDP 承载只解决「能不能到」，不解决「一定到」。理由：

- 我们的中继转发的是几百字节的唤醒信令与小块数据，可靠性由**上层业务**自己的重试决定（唤醒本来就是幂等的）；
- 自己实现重传/拥塞控制 = 重新发明一个更差的 QUIC，且没有经过任何审计；
- 把「丢包」如实暴露成 `lost`，比藏一个「自动重传了但没告诉你」的半可靠层更符合本项目的红线。

`STATUS=forwarded` 的语义严格限定为「中继转出去了」，**不表示对端应用收到**。

### 5. 与 TCP 承载并存，共用同一把 PSK 与注册语义

`--listen`（TCP）与 `--udp-listen`（UDP）可以同时开；两者的 `session` 都是 16 B 节点 id，
`HELLO` 对应 `REGISTER`，`DATA/DELIVER` 对应 `RELAY/DELIVERED`。
不共用一张注册表：TCP 连接的生命周期与 UDP 会话（带空闲回收）不同，
硬合并会让「TCP 掉线」误删「UDP 仍在」的节点——那是把两条独立的路耦合成一条。

### 6. 订阅与唤醒也走这条 UDP 路（v2.4.86）

只把「中继能转发」做出来是不够的：v2.4.85 交付的 UDP 承载只有量具会说话，
守护进程的订阅（`relay-sub`）与唤醒（`relay_wake`）都还连 TCP——
于是「中继 TCP 不可用的那台机器」永远叫不醒任何人。这一版把两侧都接到 UDP：

- **配置**：`nat.relay_udp`（可多端点）。它是**同一个中继的另一种承载**，
  不是第二个中继；`nat.relay` 与它可同时配，各自独立订阅、独立切换。
- **持有者侧**：`relay-sub` 多起一条线程，`HELLO(node_id)` → 循环
  `DELIVER` → 投给本机守护进程的唤醒端口 → 把**真实应答**投回来源会话。
  业务应答仍由守护进程产生，订阅线程不合成任何东西。
- **请求者侧**：`relay_wake_udp` 与 TCP 版逐条对应（一次性会话 id 注册、
  `DATA(target=peer)`、等 `DELIVER`），两处差别写在函数注释里：
  ① 承载不重传，调用层最多两连发（间隔 300 ms，命中即停），**不是**把 UDP 变可靠；
  ② 中继回 `STATUS` 时 `target_absent` 立刻失败——「对端没注册」和「网络慢」是两种排障方向，
  不能让调用方白等到超时。
- **保活是必须的，不是优化**：中继按 `last_seen` 回收空闲会话（默认 60 s），
  而订阅平时一条业务帧都没有。不续期就会在 60 s 后被静默删掉——
  表现为「进程还在、日志没报错、谁都叫不醒」。订阅线程每 20 s 发一次
  `PING`（`send_ping` 只发不等），`PONG` 由收包循环当普通帧忽略。
  **不能用 `UdpRelayClient::ping()`**：它读到 `PONG` 为止，会把夹在中间的 `DELIVER` 吞掉
  （等于悄悄丢一次唤醒）。
- **降级如实写**：UDP 线缆格式里没有声明帧，所以走 UDP 订阅的节点在中继看来
  `declared=false`（`lookup` 报 unknown）。这只影响「先查再打洞」的优化
  （不会替对端跳过直连），不影响送达；请求侧仍会在直连失败后落到中继。

实测（`tests/e2e/w53/udp_relay_wake.py`，23/23）：持有者 `192.168.1.221` 经
`nat.relay_udp=119.29.150.254:7101` 订阅，请求者从 `112.5.60.4` 侧唤醒，
`path=relay-udp`、`ack_status=OK`，中继计数 `data_in=2 / deliver_out=2 / mac_fail=0`；
把候选端口指到一个没监听的口后，默认路径真的先试直连（`private-lan: false`）
再落到 `relay-udp`；对照（同一中继只配 TCP 承载）唤醒失败，失败原因指向「连不上中继」。

## 后果

**好**：在被掐 TCP 的边缘上，中继第一次有了可用的原生公网路径。
实测（专用 `7101/UDP`，跨主机，v2.4.85）：**840/840、0 丢包**，
p50 落在 `34–52 ms` 区间（多次样本按载荷交替跑的结论：**RTT 与载荷大小无关**，
同一路径不同 socket 的映射会选到不同路径，故不记单一 p50 为「端口性能」），
与同路径 ICMP `25 ms`（往返）推得的理论值 `≈50 ms` 同量级，
且 A 侧 / B 侧 / 中继三处计数**逐字节**对账无缺口（`bytes_in=867232` 精确等于
`1240×280 + 440×1180 + 7×64 + 6×64`）。
`7101` 的可用性由抓包直接确认：规则加入前 `0 packets`，加入后同一口径 26 包有来有回。

**代价（照写）**：

- **无重传**：丢包只能靠上层重试，`DELIVER` 可能永远不到；
- **无拥塞控制**：`--udp-rate`（每会话报文/秒）与全局数据预算仍只在 TCP 侧，UDP 侧目前只有粗粒度 pps 限流；
- **会话是软状态**：空闲 60 s 回收，NAT 重绑定按「同 id 新地址」漫游处理（靠 MAC 证明身份）；
- **不解决 TCP 端口被掐**：原生 TCP 结论仍是 BLOCKED，本 ADR 只是绕开，不是修复；
- **不构成 S6 证据**：`s6_status=not_run`、`g2_claim=false` 不变。

## 备选（已否决）

| 方案 | 否决理由 |
| :--- | :--- |
| 再买/再开一个 TCP 端口 | §3.1 已证明边缘不看端口、不看协议内容；继续试只是把同一个结论重测一遍 |
| 用 QUIC 库自带的中继 | 引入新的依赖与 TLS 面，且不能解决「边缘掐 UDP 之外的路径」的问题；本项目协议面仍须 std-only |
| 在 UDP 上自行实现可靠传输 | 同上，且没有审计的可靠层比没有更危险（会把丢包伪装成成功） |
| 让 TCP 与 UDP 共用一张注册表 | 连接生命周期不同，耦合会制造「一条路掉了、另一条被误删」的假故障 |
