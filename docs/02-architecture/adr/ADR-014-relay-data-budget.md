## 背景

中继有两个角色：**信令桥**（所有唤醒都过它，是前置依赖）与**数据桥**（直连建不成时代收代发）。
W3.9 的公网加固只有「每连接帧速率」这道闸：默认 200 帧/秒、突发 400 帧、单帧最大 1 MiB。
按上限算，一个实例理论上可被推到数百 Mbps，足以拖垮一台小 VPS，并**连累走同一条通道的唤醒信令**。
所有者提出数据中继必须设阈值，防止中继带宽被占满后影响用户体验。

## 决策

1. **全局字节令牌桶**，不是每连接：`Limits.data_byte_rate`（默认 512 KiB/s ≈ 4 Mbps）
   与 `Limits.data_burst_bytes`（默认 2 MiB）。命令行 `--data-rate` / `--data-burst` 按部署机真实带宽调整。
2. **信令优先**：负载 ≤ `SIGNAL_FRAME_MAX`（4096 B）的帧绕过字节预算，只受原每连接帧速率约束。
   依据：WAKEUP_REQ / WAKEUP_ACK / REGISTER / 声明查询都是几百字节，而数据分片典型 ≥16 KiB。
   中继是信令前置依赖，数据面拥塞不得把唤醒一起掐断。
3. **整帧放行或整帧拒绝**，不半途截流。半帧比没帧更难归因。
4. **拒绝与「找不到目标」分开记账**：新增 `bandwidth_limited` / `bandwidth_limited_bytes`
   / `data_bytes_admitted` 三个计数，`dropped` 不变。用户侧应能区分「中继忙」与「节点离线」。
5. 同侪 `FORWARD` 在接收实例**再次计费**：每个实例花自己的上行预算，跨实例投递合计两笔。

## 备选方案与否决理由

- **只提高每连接帧速率的门槛**：帧数不是带宽，1 MiB 大帧一帧就能顶掉几千个小帧，堵不住。
- **按节点 id / IP 分配公平份额**：现在数据中继还没上线，没有真实流量分布可标定；
  先做总量护栏，等有实测再决定要不要加公平队列，避免凭想象设计。
- **把所有帧一视同仁计费**：唤醒信令会被数据流量挤掉，等于把前置依赖和数据面绑在一起死。
- **拥塞时排队等令牌**：有界队列会把一次唤醒变成不可预测的等待；宁可明确拒绝并如实计数。

## 后果与边界

- 该阈值是**部署侧资源护栏**，不是可达率承诺。它不进入 S6 判据，不产生任何公网成功率数字；
  与 [ADR-012](ADR-012-r04-best-effort.md)「工程指标可设线、外部环境成功率不设数值目标」一致。
- 默认 512 KiB/s 是按「小 VPS 留余量」选的**初始值**，不是实测最优值；部署时应按机器带宽调整。
- 4096 B 是**策略阈值**而非协议字段。若将来数据中继出现小于 4 KiB 的控制帧，它们会绕过预算——
  这是有意的（控制帧本就应优先）；真正的数据载荷应在设计时被放进大于该阈值的帧里。
- 本决策**不改任何线格式**，不需要 `PROTOCOL_VERSION` 递增；新增的只是服务端统计字段。
- 验证：`cargo test --workspace --offline` 145 passed / 0 failed，其中两条新单测覆盖
  「信令在预算耗尽时仍送达」与「数据帧整帧拒绝 + 按时间补充」；真实进程启动回显
  `RELAY_LIMITS=...,data_rate:1234/s,data_burst:4096`，stats JSON 三个新字段可解析。
- `S6.status` 仍 `not_run`，`g2_claim=false`，`evidence_valid_for_pass=false`，均不受本决策影响。
