> uTP/LEDBAT 退让机制被否证。判定记录见

## 1. 判据与目标（NFR-03）

| 项 | 阈值 | 控制手段 |
| :--- | :--- | :--- |
| 后台做种上行 | ≤ 配置阈值（默认总上行 **20%**） | 令牌桶限速（硬上限） |
| 前台吞吐劣化 | **≤ 5%** | uTP / LEDBAT 低优先级拥塞控制（退让） |

NFR-03 由**两层**共同保证，其中令牌桶是主控制、uTP/LEDBAT 是次级退让。

## 2. 控制栈设计

1. **令牌桶（主控制，硬上限）** — 见 `docs/04-protocol/CONFIG.md`：
   - `qos.background_upload_ratio = 0.2`（后台做种上行占比）
   - `qos.max_connections_total = 200`（全局连接数上限）
   - 该限速是**确定性、可单元化、本地即可验证**的：后台上行被硬卡在总上行 20%，
     无论前台是否拥塞都保证「上行 ≤ 阈值」这部分判据。
2. **uTP / LEDBAT（次级退让）— 假设已被源码否证** — `qos.prefer_utp = true`：
   - 设计意图：LEDBAT 监测单向延迟，队列延迟上升时减小发送窗口，让前台 TCP 优先占用带宽。
   - **2026-11-13 源码核实**：librqbit 9.1.0 依赖的 `librqbit-utp 0.7.0` 在
     `src/lib.rs` 首部留有 `// TODO: LEDBAT congestion control`，`CongestionControllerKind`
     **只有 `Cubic` 一个变体**，`src/congestion/` 目录下也只有 `cubic.rs`。
     因此 rqbit 的 uTP 是「带 CUBIC 的 uTP 传输」，**没有 LEDBAT 退让能力**。
   - 结论：NFR-03 第二半在当前技术栈下**只能靠令牌桶 ratio 降级**，不得宣称 uTP 会自动退让；
     若要真正启用 LEDBAT，须换实现或自行实现控制器（见 §9 与 [RISK R-07](../../../docs/05-quality/RISK.md)）。

## 3. 本地回环的根本限制（为何不能本地判 pass）

LEDBAT 的退让触发条件是**观测到单向延迟上升**。在 `127.0.0.1` 回环上，无论负载多高，
队列延迟恒为 ~0，uTP 永远**不会**触发退让。因此任何回环并发测试都**无法**锻炼真实的退让机制——
它只能证明「uTP 做种 + 前台 TCP 并发不崩溃/不死锁」（集成健壮性），但**不能**给出合法的前台劣化百分比。

> 结论：S5 的 ≤5% 判据必须经 **M1/G3 在流量整形的链路**（如 50 Mbit/s + 20ms RTT + 人为注入延迟，
> 用 `tc/netem` 或实验室链路）上实测，本地证据不足以支撑 `pass`。

## 4. 可在本地确认的可行性（已完成/可补）

- [x] **设计层去险**：令牌桶（硬上限）+ uTP/LEDBAT（退让）+ 降级链三层，R-07 在架构上已覆盖。
- [x] **rqbit uTP 能力确认（已更正）**：librqbit-utp 0.7.0 是真实 BEP 29 实现，S1 `cross-seed`/`cross-lee`
      已验证 rqbit 双 Session 真实 BT 分片传输（S1 判 `pass`）；但**拥塞控制器只有 CUBIC，无 LEDBAT**。
      §9 已用真实 uTP socket 跑通共享瓶颈量测，直接观测到「无退让」。
- [x] **令牌桶单元验证（2026-11-13 已补，见 §8）**：本地可对一个限速器实现做确定性单测，证明后台上行被卡在 ≤20%；
      这部分**不依赖网络拥塞**，可在 G0 前补一个本地 harness 直接确认 NFR-03 的第一半。
- [x] **并发瓶颈量测（2026-11-13 已补，见 §8；非真实 uTP）**：rqbit uTP 后台做种 + 前台 TCP 吞吐探针并发运行，确认无崩溃/无死锁
      （仅证健壮性，劣化数字因 §3 限制不可作为判据）。

## 5. Fallback 链（若 M1/G3 实测前台劣化 >5%）

按 LLD §降级链：接近软限 → **降低后台限速 ratio** → 停止新唤醒 → 强制切出最冷项 → **暂停造种队列**。
即在不依赖 uTP 退让的情况下，用更强的令牌桶 + 连接数限制兜底，确保前台体验。

## 6. M1/G3 可复现验证方案

1. 建一条流量整形链路：前台 TCP `iperf` 满速下载 + 后台 rqbit uTP 做种并发；
2. 测量前台 TCP 吞吐 `T0`（无后台）/ `T1`（有后台），计算劣化 `(T0−T1)/T0`；
3. 目标 `≤5%`；若超阈，调 `background_upload_ratio` 并复测，必要时启用 §5 fallback。
4. 令牌桶半独立验证：以 `background_upload_ratio=0.2` 跑后台做种，测实际上行占比 ≤20%。

## 7. 结论（2026-11-17 判定后）

`S5.status = fallback`。R-07 在设计层的两层控制里，**只有令牌桶这一层真实存在**：
`librqbit-utp 0.7.0` 无 LEDBAT，uTP 不会退让。NFR-03 的两半在默认 `ratio=0.02` 下、
于真实内核 `tc htb + netem` 链路成立（前台劣化 0.00%，3/3 轮；§10），
所以结论是**走 fallback 达成**，不是协议退让达成。

由此产生的约束：默认值 `0.02` 成了判据的一部分 —— 改回 `0.05`/`0.2` 立刻失守
（`0.2` 中位 20%；`0.05` 已有 1 轮 19.99%，未解释）。R-07 等级维持 🟠。
判定记录见 [G2-SPIKE-VERDICT-2026-11-17](../../../docs/06-plan/G2-SPIKE-VERDICT-2026-11-17.md)。

## 8. 本地真实量测（2026-11-13，补齐 §4 的 TODO）

`qos_bench.py`：真实 TCP `socketpair` 双流 + 真实时钟令牌桶 + 64 Mbit/s 应用层瓶颈整形，
三种相位（仅前台 / 前台+后台仅令牌桶 / 前台+后台+LEDBAT 式延迟退让模型），3 轮取中位数。

| `background_upload_ratio` | 后台实际上行占比（峰值） | 前台劣化（仅令牌桶） | 前台劣化（+退让模型） | ≤5% |
| :--- | :--- | :--- | :--- | :--- |
| **0.20（当前默认）** | 20.25% | **20.12%** | **15.0%** | ❌ |
| 0.05 | 5.27% | 6.19% | 6.16% | ❌ |
| **0.02（fallback 旋钮）** | 2.27% | **4.55%** | **4.03%** | ✅ |

结论：

1. **NFR-03 第一半（后台上行 ≤20%）成立**：令牌桶是确定性硬上限，与前台是否拥塞无关；三档配置均 ≤ 配置占比 + 2% 突发容差。
2. **NFR-03 第二半（前台劣化 ≤5%）在默认配置下不成立**：后台占 20% 链路时前台必然掉约 20%；
   LEDBAT 式退让模型只回收到 ~15%。**M1 默认值不得沿用 0.2 即声称满足 NFR-03**，须按实测回调或启用 §5 fallback 链。
3. **fallback 有效**：把 ratio 降到 0.02 后本地劣化进入目标区间，给了 M1 一个可执行的参数起点。
4. 退让控制器是**LEDBAT 机理的可执行模型**，不是 librqbit uTP；瓶颈也是应用层整形而非真实链路排队。
   按 README §6 第 3 条，这些数字**不能支撑 `pass`**，只用于定位参数与验证 harness 骨架。
5. **§8 的「+退让模型」一栏在真实 rqbit 栈上不成立**：源码核实无 LEDBAT，§9 的实测也显示
   前台劣化与后台实际占用近似 1:1，没有出现模型预测的「退让回收」。

## 9. 真实 librqbit-utp 协议栈拥塞量测（2026-11-13 第二次更新）

`utp/` 是独立 Cargo 工程（不并入 std-only 根 workspace，`cargo build --offline --release` 可复现）。
与 `qos_bench.py` 的本质区别：**后台是真实 `librqbit-utp 0.7.0` BEP 29 栈**，真实 UDP socket、
真实 SYN/ACK/窗口/重传；前台 TCP 与后台 uTP 争用**同一个真实时钟令牌桶瓶颈**，
排队用真实 `sleep` 产生（实测最大排队等待 16–32 ms、均值 2–5 ms），uTP 观测到的是真实 RTT 膨胀。

```bash
cd tests/spikes/s5/utp && cargo build --offline --release
target/release/coldrevive-s5-utp-probe.exe \
  --seconds 3 --rounds 3 --ratios 0.2,0.05,0.02 --link-mbps 16 \
  --out reports/s5-utp-real-20261113.json
```

16 Mbit/s 链路、每相位 3 s、每档 3 轮取中位数：

| `background_upload_ratio` | 后台实际链路占比（中位） | 前台劣化（中位） | 逐轮劣化 | NFR-03 ≤5% |
| :--- | :--- | :--- | :--- | :--- |
| **0.20（原默认）** | 14.6% | **14.82%** | 15.86 / 12.97 / 14.82 % | ❌ |
| 0.05 | 5.4% | **4.31%** | 4.58 / 4.31 / 3.78 % | ✅ |
| **0.02（M1 现行默认）** | 3.1% | **2.70%** | 2.96 / 2.70 / 2.70 % | ✅ |

关键结论：

1. **真实 uTP 栈没有退让**：三档的「前台劣化」与「后台实际链路占比」几乎 1:1
   （14.8%↔14.6%、4.3%↔5.4%、2.7%↔3.1%），不存在 §8 模型预测的「LEDBAT 回收约 5 个点」。
   与源码 `// TODO: LEDBAT congestion control` + 仅 `Cubic` 变体完全吻合。
2. **NFR-03 第二半只能靠令牌桶**：M1 已把默认 `background_upload_ratio` 从 `0.2` 回调为 `0.02`
   （[CONFIG](../../../docs/04-protocol/CONFIG.md) 2.1），本次真实协议栈量测给出 2.70% 劣化，
   支持该回调；但这是**降级链生效**，不是 uTP 退让达标。
3. 与 §8 模型数值不同（0.2 档模型 15.0% / 实测 14.82%；0.05 档模型 6.16% / 实测 4.31%），
   原因是模型假设 uTP 会退让且用固定整形，实测是真实窗口控制。**以实测为准**。
4. **范围限制（2026-11-13 时点）**：当时的瓶颈是本机用户态整形，不是 `tc/netem` 内核队列。
   该缺口已于 2026-11-17 由 §11 补齐；本条保留为历史记录，不再是当前状态。

报告：`reports/s5-utp-real-20261113.json`（本地产物，按 spike 惯例不入库）。
机读结论与风险升级登记在 `tests/spikes/spikes.json` 的 `S5.observations.utp_real_2026_11_13`。

报告：`reports/s5-qos-final-ratio020.json` / `...ratio005.json` / `...ratio002.json`（本地产物、不入库）。

## 10. 真实 uTP 栈 5 轮复跑（2026-11-14 / W3.5①）

用同一份 `librqbit-utp 0.7.0` 真实协议栈把 §9 的 3 轮扩到 5 轮复核：

| `background_upload_ratio` | 后台实际链路占比（中位） | 前台劣化（中位） | 各轮 | ≤5% |
| :--- | :--- | :--- | :--- | :--- |
| `0.2`（原默认） | 15.09% | **14.78%** | 16.4 / 12.1 / 14.78 / 15.9 / 13.17 | ❌ |

## 11. 真实内核拥塞链路量测（2026-11-17，tc/netem）

`utp_netem/` 是独立 Cargo 工程 + `run_netem.sh` 驱动，在 221（root）上建跨 netns veth，
出口 `v5a` 挂内核 `htb 16 mbit + netem delay 20ms 2ms`，跨 netns ping RTT 实测
**19.9 / 27.0 / 41.0 ms**（证明 netem 生效）。前景为单条连续 `iperf3 -J -i 1 --congestion bbr`
TCP 会话，后台为真实 `librqbit-utp 0.7.0` 双进程（分处两 netns）。
每轮在**同一条** iperf3 会话内比较 baseline(5 s) / concurrent(10 s) / recovery(5 s) 区间的中位吞吐。

> 为什么必须单会话比较：首版用「独立 baseline 会话 + 独立 concurrent 会话」，基线在
> 14.7–20.6 Mbit/s 之间跳，算出来的「劣化」有时是负的。同一连接内的区间对比把这个噪声消掉。

```bash
cd tests/spikes/s5/utp_netem
S5_BASE=5 S5_CONC=10 S5_REC=5 S5_ROUNDS=3 \
S5_RATIOS=0.2,0.05,0.02 S5_CONGESTION=bbr bash run_netem.sh
```

| 配置 ratio | 后台实际占比（中位） | 前台劣化（中位） | 逐轮劣化 | ≤5% |
| :--- | :--- | :--- | :--- | :--- |
| 0.20（原默认） | 0.1252 | **20.00%** | -0.01 / 20.00 / 20.00 % | ❌ |
| 0.05 | 0.0496 | **0.01%** | 19.99 / 0.00 / 0.01 % | ⚠️ 中位达标，但 1/3 轮劣化 19.99% |
| **0.02（现行默认）** | **0.0199** | **0.00%** | 0.00 / -0.01 / 0.00 % | ✅ |

原始报告：`reports/s5-utp-netem-20261117.json`（按 `.gitignore` 不入库）。

**读数注意**：0.20 档的后台实际占比只有 0.1252，不是 0.2 —— 3.2 Mbit/s 的配额在
16 Mbit/s + 20 ms 的链路上，uTP 自己没有打满。所以「劣化 20%」是**配置配额的体现**，
不是「后台真的占了 20% 带宽」。这不影响结论方向，但别把它当成比例换算。

**未解释的观测**：0.05 档有一轮劣化 19.99%，与后台实际只占 0.049（0.79 Mbit/s）不相称。
怀疑是 iperf3 区间跨到相边界（未证实）。**不得据此认为 0.05 可用**，也不得把它当成 5% 的证据。

## 12. 判定：`fallback`（2026-11-17，所有者）

| 项 | 值 |
| :--- | :--- |
| `S5.status` | **`fallback`** |
| 依据 | 真实内核链路 + 真实 uTP 栈：默认 `ratio=0.02` 前台劣化 0.00%（3/3 轮）；机制为令牌桶 |
| 为什么不是 `pass` | Spike 标题主张的 uTP/LEDBAT 退让为假（`librqbit-utp 0.7.0` 仅 CUBIC） |
| 为什么不是 `fail` | NFR-03 的两半在默认配置下达成，走的是早就登记过的 fallback 链 |
| 约束 | 默认值锁 `0.02`；回调到 `0.05`/`0.2` 即失守；换链路形状须重跑 |
| 判定记录 | [G2-SPIKE-VERDICT-2026-11-17](../../../docs/06-plan/G2-SPIKE-VERDICT-2026-11-17.md) |

**边界**：只在 16 Mbit / 20 ms / 单机双 netns 上测过，**不是跨物理主机**；
报告固定 `evidence_valid_for_pass=false`；不得写「任意链路下前台劣化 ≤5%」。
