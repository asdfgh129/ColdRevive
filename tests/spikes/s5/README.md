# S5 spike：uTP / LEDBAT 后台退让满足 NFR-03

> **状态（2026-11-11）：`not_run`。** 判据要求「前台下载与后台做种并发时前台吞吐退让符合预期」，
> 本质是**真实网络拥塞下的退让行为**，无法在 127.0.0.1 回环上忠实复现（见 §3 限制）。
> 本目录给出控制栈设计、rqbit 能力确认、可在 M1/G3 执行的可复现验证方案与 fallback 链；
> 最终 `pass` 须 M1/G3 在**带流量整形的链路**上实测前台劣化 ≤5%。

## 1. 判据与目标（NFR-03）

| 项 | 阈值 | 控制手段 |
| :--- | :--- | :--- |
| 后台做种上行 | ≤ 配置阈值（默认总上行 **20%**） | 令牌桶限速（硬上限） |
| 前台吞吐劣化 | **≤ 5%** | uTP / LEDBAT 低优先级拥塞控制（退让） |

NFR-03 由**两层**共同保证，其中令牌桶是主控制、uTP/LEDBAT 是次级退让。

## 2. 控制栈设计

1. **令牌桶（主控制，硬上限）** — 见 `docs/04-protocol/CONFIG.md`：
   - `qos.background_upload_ratio = 0.2`（后台做种上行占比）
   - `qos.max_connections_total = 200`（全局连接数上限）
   - 该限速是**确定性、可单元化、本地即可验证**的：后台上行被硬卡在总上行 20%，
     无论前台是否拥塞都保证「上行 ≤ 阈值」这部分判据。
2. **uTP / LEDBAT（次级退让）** — `qos.prefer_utp = true`：
   - LEDBAT 监测单向延迟（one-way delay），当后台 uTP 流量导致队列延迟上升（即前台 TCP 开始排队）时，
     自动减小发送窗口退让，让前台 TCP 优先占用带宽，从而达成「前台吞吐劣化 ≤5%」。
   - librqbit 已支持 uTP（μTP）传输层；`prefer_utp` 配置项已存在于 `CONFIG.md`，机制可用。

## 3. 本地回环的根本限制（为何不能本地判 pass）

LEDBAT 的退让触发条件是**观测到单向延迟上升**。在 `127.0.0.1` 回环上，无论负载多高，
队列延迟恒为 ~0，uTP 永远**不会**触发退让。因此任何回环并发测试都**无法**锻炼真实的退让机制——
它只能证明「uTP 做种 + 前台 TCP 并发不崩溃/不死锁」（集成健壮性），但**不能**给出合法的前台劣化百分比。

> 结论：S5 的 ≤5% 判据必须经 **M1/G3 在流量整形的链路**（如 50 Mbit/s + 20ms RTT + 人为注入延迟，
> 用 `tc/netem` 或实验室链路）上实测，本地证据不足以支撑 `pass`。

## 4. 可在本地确认的可行性（已完成/可补）

- [x] **设计层去险**：令牌桶（硬上限）+ uTP/LEDBAT（退让）+ 降级链三层，R-07 在架构上已覆盖。
- [x] **rqbit uTP 能力确认**：librqbit 9.1.0 支持 uTP；S1 `cross-seed`/`cross-lee` 已验证 rqbit 双 Session
      真实 BT 分片传输（S1 判 `pass`），uTP 传输是该引擎的标配能力。
- [ ] **令牌桶单元验证（建议补）**：本地可对一个限速器实现做确定性单测，证明后台上行被卡在 ≤20%；
      这部分**不依赖网络拥塞**，可在 G0 前补一个本地 harness 直接确认 NFR-03 的第一半。
- [ ] **并发集成烟雾测试（可选）**：rqbit uTP 后台做种 + 前台 TCP 吞吐探针并发运行，确认无崩溃/无死锁
      （仅证健壮性，劣化数字因 §3 限制不可作为判据）。

## 5. Fallback 链（若 M1/G3 实测前台劣化 >5%）

按 LLD §降级链：接近软限 → **降低后台限速 ratio** → 停止新唤醒 → 强制切出最冷项 → **暂停造种队列**。
即在不依赖 uTP 退让的情况下，用更强的令牌桶 + 连接数限制兜底，确保前台体验。

## 6. M1/G3 可复现验证方案

1. 建一条流量整形链路：前台 TCP `iperf` 满速下载 + 后台 rqbit uTP 做种并发；
2. 测量前台 TCP 吞吐 `T0`（无后台）/ `T1`（有后台），计算劣化 `(T0−T1)/T0`；
3. 目标 `≤5%`；若超阈，调 `background_upload_ratio` 并复测，必要时启用 §5 fallback。
4. 令牌桶半独立验证：以 `background_upload_ratio=0.2` 跑后台做种，测实际上行占比 ≤20%。

## 7. 结论（当前）

R-07（造种/做种 I/O 影响前台）在**设计层已去险**：双层控制（硬限速 + uTP 退让）+ 明确 fallback。
量化「前台劣化 ≤5%」待 M1/G3 真实拥塞链路实测；在此之前 `S5.status = not_run`，
不回滚技术路线。S4/S7 已证明内存与造种开销本身不构成前台威胁。
